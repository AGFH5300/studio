# Veya Fold — Phase 2 evidence and verdict

Date: 2026-09-07. **CONDITIONAL PASS — WEBGL VISUAL GATE UNVERIFIED.** This does not reject the Fold concept. It means this run has not established the physically convincing, beautifully lit browser object required before scaling it.

## What is genuinely verified

A development-only `/lab/fold` route implements a side-bound folio in browser-native CSS 3D with real HTML/SVG surfaces. The closed website opens around a fixed asymmetric spine to reveal a shared content source and a narrower mobile wing. Three principal surfaces maximum. A local React headline updates the physical representations and two normally readable HTML previews. The original fictional Saha Retreat illustration is authored SVG; no real company or research image is used.

Personally inspected browser captures cover closed, 25%, half, 75%, open, content edit, mobile initial/open/edit and a hinge detail. Real controls were operated: open, reverse, enter different headline values on desktop and mobile. The field's value appeared in both HTML article previews, verified from rendered DOM, as well as visually on the object. No backend is implied. Starting price and business proposition remain ordinary HTML.

**These are CSS 3D screenshots, not WebGL screenshots or Blender renders.** CSS edge shading and a composited ground shadow do not prove physically based materials, light transport, contact shadows or mesh collision freedom.

## Mechanics and state

- CSS authoring frame: 340 × 265; spine projects above and below; front leaf pivots at x=-9; back content chassis remains fixed. Narrow wing folds from the right axis. Front leaf has two finished faces: it is a duplex display folio, not paper with magically persistent front-facing text.
- Fixed endpoint rotation: front -165°, wing 170° of travel. CSS transitions are 1200 ms and interruptible; changing target replaces the current transition. No command queue or physics engine.
- Application state: `headline`. Presentation state: `pose`, clay/study/instant diagnostics. Neither animation nor rendering writes content or pricing.
- Mobile: frontal view, same spine, one active interior surface, no right wing, normal vertical scroll. Closed leaf can extend outside the intentionally cropped mobile inspection window; its blank reverse is not another information surface.
- Forced instant fixture computes `transition-duration: 0s`; an OS reduced-motion CSS rule is present. OS-level emulation was unavailable and is not claimed tested.
- CSS/HTML appears without canvas. On WebGL failure it remains available; all essential business/content information is independent. Poster-quality source composition retained; final compressed poster exports are not produced.

## Measurements and limits

Measured two 120-frame browser requestAnimationFrame windows around CSS interactions: desktop mean 60.0 fps, p95 16.8 ms, max 16.8 ms; mobile viewport mean 60.0 fps, p95 16.8 ms, max 16.8 ms. These are callback intervals in the cloud browser, **not GPU presentation measurements or physical-phone performance**. No claim of sustained device performance.

One successful production build measured isolated Fold chunks: CSS 11,796 bytes / 3,430 gzip; component JS 9,321 / 3,436 gzip; optional scene module 7,176 / 3,412 gzip. These exclude shared React/Three dependencies and existing site assets and are not an initial-route transfer total. Final checksums and per-source bytes are in the manifest. No external texture/HDRI/model requests are required by the CSS version. WebGL triangles/draw calls/texture footprint unavailable because context creation failed. Budget goals remain 4/2 MB, 150K/60K triangles, 80/40 draws, 60/30 fps; no GPU budget is claimed passed.

## Final self-critique and next dependency

Creative direction: remove extra decoration; keep the spine and restrained palette. Industrial design: current foot/spine is suggestive, not an engineered load path; verify solid geometry and joint clearance in GPU authoring. Interaction: the source reuse works; improve editor/scene proximity only after the visual gate. Business: preserve current clear proposition and honest fictional labeling. Engineering: keep content independent, choose one production rendering approach after visual validation, and remove unused experiment code when that choice is made.

**Do not start the full estimator.** Smallest next step is a GPU-enabled verification of the selected folio: build/inspect neutral solid geometry, fix silhouette if it still resembles a display device, then establish an independent closed/half/open material target and match it in actual runtime. Preserve the local CMS interaction and mobile composition as validated starting points. No new concept, room, particles or larger feature scope is warranted.

### Side-bound identity review

The folio is intentionally book-like in its opening verb; that helps comprehension, but the large rectangular face still carries most of its identity. It does not read as a laptop: there is no keyboard, horizontal base or laptop hinge. The cobalt spine owns the hinge barrels and extends to the foot, so it explains structure rather than merely outlining a screen. The open state remains one joined object, and the half-open state is comprehensible in the fallback. The source panel explains website-to-system; the actual CMS edit supplies stronger proof than the static metaphor alone. Brand recognition is **provisional**, not proven distinctive enough for full-site repetition. Do not add decoration to conceal that uncertainty. Next physical pass should retain the spine/foot relationship and test solid edge geometry and silhouette under neutral light before any expansion.
