# Veya Labs — complete experience map

## First load and hero

**0–5 seconds:** deliver server-rendered navigation, proposition, “Projects from AED 999”, Build your project and See our work with a carefully framed poster of the Fold. The initial poster is already a complete composition. No entrance gate, percentage counter or compulsory movie. Text and links work before 3D.

**5–15 seconds, if capable and ready:** match the live scene exactly to the poster and quietly replace it. Show one short hinge movement to indicate “See what makes it work”; stop. Never run a perpetual demo. If assets are late, the poster stays attractive and useful.

**First interaction:** clicking that labelled control unfolds the sample site, revealing its page family and service path. The same control exists as a keyboard-accessible HTML button. The small orbit region never captures page scrolling. Stop/pause or reduced motion immediately resolves to the selected state.

**First CTA:** Build your project is visible from the initial response. Clicking opens `/build` and carries only explicitly selected demo choices if the visitor accepts “Use this as a starting point.” Exploring a sample must not silently fill the estimator.

## Navigation and route map

Persistent desktop navigation: **Work · Services · Pricing · About · Build your project**. Contact is a visible text link in the header or utility area and footer. Process is on the home page and linked from Services/Pricing; give it `/process` for direct access. This reduces competing primary items while retaining all required content. Mobile header: logo, Build, Menu. Menu is a proper focus-managed dialog with all routes.

| Route | Purpose / content | Interaction | Main next action |
|---|---|---|---|
| `/` | Proposition, signature demonstration, selected work, services, package preview, process, concise FAQ, contact | Fold, CMS edit, sample enquiry | Build or work |
| `/work` | Evidence-first project index; sector/capability filters only if enough projects | Select a project | Case study |
| `/work/[slug]` | Problem, brief, actual contribution, experience, systems, evidence, limitations, credits | Try one bounded demonstration; front/inside views | Start a similar project |
| `/services` | Websites, ecommerce, custom experiences, integrations, AI/automation | See outcome → demo → scope | Relevant service or Build |
| `/services/[slug]` | One substantive service page: outcomes, deliverables, process, scope, FAQ | Optional lightweight demo | Build with explicit prefill |

| `/build` | Six-part estimator, visual system, summary, copy/share, inquiry | Configure, back, undo, test, finish | Build this with Veya |
| `/process` | Discover → design → build → launch → support | Small before/after deliverable examples | Discuss project |

No fabricated locality pages, invented office, clients, certifications, testimonials, awards or conversion metrics. Work for the founders’ own projects must be labelled accurately; it is not automatically Veya client work. Concept work is clearly labelled “Concept project” in listings and detail pages.

## Estimator experience on the page

Desktop: 58–65% project stage and 35–42% comfortable editing panel, with visible question title, selected scope and investment status. Six labelled chapters remain directly reachable. The next button is a convenience, not a lock. Completed chapters have a quiet check; unknown answers show “Needs discussion”, never a false complete check.

Mobile: a 180–240px frontal project preview above the active question; it collapses to a slim scope strip when the keyboard appears or the user scrolls into long controls. Controls are in the page, not a cramped bottom sheet. A sticky summary button shows scope status and opens the full summary. No automatic jumps to keep the illustration visible.

Business effects update immediately in HTML. The renderer then moves toward the latest derived state. Fast repeated choices cancel intermediate animations. It must never replay a long queue.

## Work presentation

Every case has: a real business problem; Veya/founder role and exact scope; 3–5 representative views; one useful interactive example if permission exists; constraints and tradeoffs; implementation explanation in buyer language; genuine evidence. Prefer a functioning miniature enquiry or booking demonstration over a rotating screenshot wall. Do not embed arbitrary production websites inside 3D if framing, permissions or credentials are uncertain. Use authored demo data and accurate screenshots with explicit provenance.

Selecting a case expands the front face into a full HTML layout. The URL changes normally and browser Back works. Reduced-motion mode uses immediate navigation. “Inside this project” reveals the system map with readable labels; the main page still contains equivalent prose. A case may be fully static and still qualify if its evidence is strong.

## Services and pricing

Describe services by outcomes: **Be found and trusted; sell online; connect your tools; reduce repetitive work; build something distinctive.** Under each, state actual deliverables and dependencies, then link to a specific service page. A visible sample result is more useful than a row of vendor logos.

Pricing stays in HTML, accessible without horizontal dragging. Desktop comparison table; mobile one package per section with a consistent comparison list. Preserve Starter AED 999, Pro AED 2,499, Business AED 4,999, Signature AED 9,999+. Explain that Veya’s own flagship is a custom experience; AED 999 describes the defined entry scope, not replication of this entire website. Do not label every feature as included until the commercial catalog is approved.

Separate project implementation fees from domain, hosting, paid platforms, payment processing and AI usage. Specific VAT treatment, deposits, included integrations and timelines remain business-owner decisions before public release. No fabricated turnaround promises.

## Process, about and contact

Process shows concrete deliverables: an agreed scope; design direction and page layouts; working implementation and review; launch checklist and handover; stated support period. Explain revisions versus new scope in plain language once commercial definitions are confirmed.

About uses actual people and verifiable work. Explain small-team access, design review, integrations, and post-launch responsibility without pretending to be a large agency. UAE relevance comes from AED pricing, local contact details when supplied, Dubai/Gulf time handling and realistic regional business examples, not desert ornamentation.

Contact requires name, one reply address (email), and a short project message; company, phone, budget and timing optional. If the estimator was used, include a readable expandable summary that the user can remove. Separate any marketing consent. Do not request sensitive customer data. User chooses Send inquiry; no hidden automatic mailing, calendar booking or CRM write from experimentation.

Show submitting, received, delayed and failure states distinctly. A success message means the server accepted the inquiry, not that a human read it. Preserve text on errors. Provide a real configured email fallback and copy-brief action. A booking link can follow successful submission; it must not replace contact and must use a verified owner-provided URL.

## AI demonstration

Launch candidate: **Turn this enquiry into a useful next step.** Use synthetic restaurant, professional-service or retail enquiries. A small server-side model call returns structured intent, requested service and a draft reply against an authored demo knowledge base. Show source snippets, editable interpretation and the draft. Send nothing externally. CRM and automation events run in a bounded local simulation, visibly labelled “Demo”.

A model response cannot set prices or mutate estimator selections. “Apply suggested capabilities” presents a diff and requires a click; it dispatches the same validated commands as manual controls. If live AI is unavailable, retain a labelled recorded example with no typing theater or claims of real-time intelligence. The estimator and site remain complete without the model call.

## Microinteractions and accessibility behavior

Selection: decisive visual press and readable selected label. Dependency: inline explanation with explicit add/remove confirmation. Undo: restore user intent and scope together. Price status: no gambling-counter animation; one polite announcement after the choice settles. Loading: local to the component. Focus: stays on the triggering control; summary links focus the relevant chapter heading. Tooltips supplement labels, never replace them. No essential hover-only content.
